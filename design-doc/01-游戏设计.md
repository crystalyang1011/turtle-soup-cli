# 01 · 游戏设计

> 本章是 v2.0 新增的**游戏设计层**，也是整份文档的地基。v1.0 只写了工程，没写"怎么玩才算玩得好"。
> 所有数值是本项目自定的**首版基准**，M1 用真实对局回放校准（见 [08 §3 测试策略](08-工程化与验收.md)）。

---

## 1. 核心体验与循环

**一句话体验**：一个人对着一个"只肯回答是/否"的 AI 主持人，靠提问把碎片拼成真相，拼到 70% 时敢不敢"翻底"。

**单局循环**（这就是全部玩法，别再加爬塔/抽卡）：

```
出题（看汤面）
  → 读题、在脑子里建模
  → 提问（是 / 否 / 无关 / 部分）
  → 判定 + 进度条前进（命中 key_fact）
  → 信息不足？要真话（少花钱）还是要提示（花钱）
  → 自认拼够了 → 猜底
  → 赢 / 差一点 → 回到提问
```

**设计红线**：

- **不做数值成长**。没有金币、等级、体力。摸鱼工具的一切成长系统都是工时杀手。
- **单局 3–8 分钟**。超过 8 分钟还推不动的题，玩家会弃局，弃局不惩罚。
- **进度条是安慰剂也是诱惑**。它让玩家知道"离真相还有多远"，从而在 70% 时纠结要不要翻底——**这个纠结就是游戏的心跳**。

---

## 2. 一局的标准流程

| 阶段 | 玩家动作 | 系统行为 | 可挂起 |
|---|---|---|---|
| 出题 | 选难度 / 随机 或 从题库挑 | 展示汤面、进度条 0/6、剩余提示次数 | — |
| 追问 | 输入问题或陈述 | 一次主持人调用 → `judgment` + `hit_facts` → 进度条前进 | ✅ |
| 提示 | 点"提示" | 按 §5 两级提示消耗 | ✅ |
| 猜底 | 点"我要猜汤底"，输入完整推理 | 一次猜底调用 → 评分 → 赢或回追问 | ✅ |
| 结算 | 查看汤底 + 得分星级 | 展示真相、得分、本局统计 | — |

**回合内并发约束**：判定调用期间输入框禁用（防重复提交），超时 20s 见 [07 §4](07-安全与异常.md)。

## 3. 目标函数：评分与星级

v1.0 只记录 `questionCount` / `hintsUsed` 却不定义用途。这里补上唯一的目标函数。

### 3.1 单局得分

```
par(difficulty) = 5 + 3 × difficulty          # 基准问数：D1=8, D2=11, D3=14, D4=17, D5=20

raw = 100
raw -= 2 × max(0, questionCount - par)        # 超出基准问数才罚，低于基准不额外奖
raw -= 12 × hintsUsed                          # 提示很贵（见 §5）
raw -= 8  × guessAttemptsFailed                # 每次猜底失败
raw = max(0, raw)

score = round( raw × (1 + 0.2 × (difficulty - 1)) )   # 难度系数：D1×1.0 … D5×1.8
```

设计意图：**"问得少"有硬上限收益**（低于 par 不奖，避免玩家硬猜），**"用提示"是重罚**（一次提示≈6 个问题），从而把提示变成"卡死才用"的止损项。

### 3.2 星级（三档）

| 星级 | 条件 |
|---|---|
| ★★★ | 0 提示 且 questionCount ≤ par |
| ★★ | hintsUsed ≤ 1 |
| ★ | 通关（win）即得 |

星级只用于自我评价与二期战绩统计，不做解锁门槛。

### 3.3 记录而不评分的字段

`hintsUsedDetail`（每次提示的类型/耗时）记录但不计入分数，为二期"题型弱项分析"留数据。

## 4. 胜负精确规则（消歧版）

v1.0 的 `hit_ratio >= 0.7 且因果链完整` 有两个坑：阈值与事实数耦合、因果链靠 AI 主观判断。修正如下。

### 4.1 赢的条件（全部满足）

```
1. hit_ratio >= 0.7                       # hit_facts 去重命中数 / key_facts 总数
2. 所有 core=true 的 key_fact 均命中       # 把"因果链完整"变成客观可查，不靠 AI 打分
```

- `hit_ratio` 由 `engine.rs` 本地计算（命中数 / 总数），**不采信 LLM 返回的 hit_ratio**（LLM 只返回 `missed_facts`，见 [05 §2](05-Prompt设计.md)）。
- `core` 事实 = 因果链的"因"与"果"，在 ETL 阶段标注（见 [04 §3](04-题源与ETL.md)），每题 1–2 条。

### 4.2 事实条数与阈值的关系（防退化）

| key_facts 条数 | 0.7 阈值需命中 | 说明 |
|---|---|---|
| 3 | 3（全中） | 太严，禁止单题只有 3 条；ETL 要求 ≥4 |
| 4 | 3 | 可接受 |
| 5 | 4 | 推荐 |
| 6 | 5 | 推荐上限 |

**规定：key_facts 条数 ∈ [4, 6]**（v1.0 的 3–5 收紧为 4–6），避免"3 条必须全中"的退化。

### 4.3 猜底失败反馈（反泄底）

v1.0 写"展示未命中事实列表" = 把剩下的答案直接念给玩家。**改为只给三项**：

1. 未命中**条数**（`missed_count`，不给条目）；
2. 一句 30 字内方向性点评（prompt §2 已禁止复述事实原文）；
3. 剩余猜底次数。

### 4.4 猜底次数耗尽

```
猜底期间        → 失败 → 回 qa_loop（若剩余次数 > 0）
失败第 3 次     → status = lost，展示汤底 + "再来一局"，本局结束
```

`lost` 是**可达的终态**（v1.0 状态机只画了 won/abandoned，`lost` 悬空）。

### 4.5 多解与创造性答案

海龟汤常有多解，单真值模型会误杀合理答案。策略：

- **判定以 key_facts 为准**，但猜底 prompt 显式允许"语义等价、机制一致的变体"计命中（例：把"打嗝"换成"膈肌痉挛"仍命中）。
- 若玩家给出**与 key_facts 不同但逻辑自洽**的完整解：prompt 要求裁判在 `comment` 中说明"自洽但与本题机制不同"，**本局记为 lose 但不算入连续失败**（不扣 `guessAttemptsFailed` 的分数惩罚，只消耗次数），给玩家台阶下。
- 二期可选：为高争议题补 `alt_truths[]` 备用解。MVP 不做。

## 5. 提示系统与经济

v1.0 的提示"直接揭示一条事实"= 花钱买答案，还只有惩罚没有分层。改为**两级提示**：

| 级别 | 内容 | 成本 | 是否推进进度条 |
|---|---|---|---|
| L1 方向提示 | 指向尚未命中的**大方向**，不揭示事实原文（如"想一想他为什么偏偏要水"） | `hintsUsed += 0.5` 折算，扣 6 分 | ❌ 不前进 |
| L2 事实提示 | 按 key_facts 顺序揭示一条**未命中**事实的原文 | `hintsUsed += 1`，扣 12 分 | ✅ 该事实计入命中 |

规则：

- 先 L1 后 L2：同一事实未用 L1 也能直接 L2，但跳级不省分。
- 每局提示次数上限 = `ceil(key_facts / 2)`，用完为止。
- 揭示顺序：**先非 core 事实，后 core 事实**，避免提示直接送掉胜负硬条件。
- L1 提示文本可以预生成（ETL 阶段为每条 fact 写一句方向句）或运行时由出题/提示模型生成；MVP 用运行时生成，缓存到 session。

**经济意图**：L1 便宜、能救急但不泄底；L2 贵、直接推进度条。玩家会先熬着不点提示。

## 6. 难度分档与题目推荐

### 6.1 难度定义（写死，避免主观）

| difficulty | 定义（汤面与汤底语义距离 + 常见误解层数） | 基准问数 par |
|---|---|---|
| 1 | 单因果直给，1 层误解 | 8 |
| 2 | 单因果带反常动机，1–2 层 | 11 |
| 3 | 双因果需并联，2 层 | 14 |
| 4 | 存在强误导性表面叙事，3 层 | 17 |
| 5 | 多层因果 + 需要放弃一个错误前提 | 20 |

ETL 阶段由人工按上表打难度（dataset 里通常无此字段），AI 只做初判、人工终审。

### 6.2 选题/推荐（MVP 保持简单）

- 入口：**随机一题** 或 **按难度筛** 或 **从题库列表手动挑**。
- 随机权重：未通关题优先；同难度不连出（避免连续挫败）。
- 不做"自适应难度"——数据量不够，二期再议。

## 7. 边界输入处理（v1.0 缺失）

主持人对以下输入的行为必须明确，否则玩家会困惑：

| 输入类型 | 例子 | 处理 |
|---|---|---|
| 复合问题 | "他是不是先打嗝，然后老板才掏枪？" | 判定为 `partial`，reply 指出"对了一半"，`hit_facts` 只记确实成立的；不拆成两问 |
| 猜测当提问 | "因为他要水止嗝？" | 正常判定：命中则 `yes` + hit_facts，reply 仅"是"（防泄底规则 8） |
| 元问题 | "这游戏怎么玩？""还有几个事实？" | `irrelevant`，reply 给固定引导语（不进 prompt 记忆），不透露事实数 |
| 求答案 | "直接告诉我汤底" | `irrelevant` + 拒绝话术；**这条同时是注入攻击入口，见 [07 §2](07-安全与异常.md)** |
| 超长输入 | 粘贴 500 字小作文 | 截断到 500 字符再送 LLM，UI 提示已截断 |
| 空 / 纯符号 | "" / "???" | 前端拦，不发请求 |
| 打错字 / 口语 | "他四不四打嗝" | 正常语义判定，prompt 已要求容错 |

## 8. 主持人调性（人格设计）

v1.0 只把主持人当判定器，reply ≤20 字且禁一切评价。补一个人设，但**不得牺牲反泄底**：

- 人设：**冷面、惜字如金的老裁判**。只答事实，不陪聊、不安慰、不评价。
- 允许的语气词仅限判定本身（"是""否""无关""对了一半"），**禁止**"接近了""加油""有意思"。
- 这与 [05 §1 防泄底铁律](05-Prompt设计.md) 不冲突：人格体现在"克制"，不是"话多"。
- 结算阶段（win/lose）可放一句固定风格点评，此时已可揭示汤底，不受泄底限制。

## 9. 留存与"好玩"验收指标（v1.0 的"验证好玩"落地）

二期才写"验证好玩"，但 MVP 就要有可判定的目标，否则 M4 无法验收。

**MVP 好玩验收口径**（自用工具，人工主观打分 + 客观记录）：

1. **单局完成率**：随机 10 局，主动弃局 ≤ 3 局；
2. **复玩意愿**：连续完成 2 局后仍主动点"再来一局"；
3. **翻底冲动**：进度条到 60%+ 时玩家出现"要不要猜"的犹豫（主观，自评即可）；
4. **判定可信**：主观认为"主持人判错了"的比例 ≤ 10%。

记录数据（胜率、平均问数、平均提示数）落 `stats.json`，二期做可视化。**MVP 不做 UI，只记数据。**

## 10. 玩家旅程与首启

> v3.0 起只有 CLI，没有设置页/界面。本节按命令行旅程描述。

| 场景 | 期望行为 |
|---|---|
| 首次使用 | 在项目根放 `config.json`（复制 `config.example.json`，填 `base_url`/`model`/`api_key`）→ `soup-cli list` 应能列题 |
| 无 Key / 配置错 | 启动即报**可读错误**并给出配置文件路径与日志路径（见 [07 §4](07-安全与异常.md)） |
| 题库为空 | 提示 `soup-cli fetch` 拉题（需联网） |
| 通关/失败 | 终端展示汤底 + 得分星级；可 `play` 再来一局 |
| 恢复中途对局 | `soup-cli play --resume <id>`；启动 `play` 时若有未完成对局也提示可选恢复 |

**命令与配置入口**（替代原设置页）：

- 配置：`config.json`（`base_url` / `api_key` / `model` / `host_model`；Key 优先级 env `TURTLE_API_KEY` > 内联）。
- 题库：`soup-cli fetch`（拉题）、`soup-cli list`（查看）。
- 摸鱼：终端标题伪装、低对比输出、`Ctrl+C` 快速退出（见 [06](06-摸鱼特性.md)）。
- 诊断：日志在 app data `logs/app.log`，`soup-cli config` 打印路径。

## 11. 明确不做（游戏层）

- 数值成长、体力、抽卡、每日任务、签到；
- 多人/联机/排行榜；
- 云同步、账号体系；
- 自适应难度、动态生成题（二期+人工审核后才考虑）。
